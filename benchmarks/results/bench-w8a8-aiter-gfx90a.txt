NOTE ON COMPARABILITY -- this is NOT llama-bench output.
The table above is formatted to match llama-bench for side-by-side reading, but
it was produced by build/bench_llamabench_style.py driving a vLLM OpenAI server
over HTTP. Differences that matter:

  * Quant differs. Reference runs used llama.cpp Q8_0 (26.62 GiB). This is
    compressed-tensors W8A8 INT8 (29.10 GiB): int8 weights, channel strategy,
    int8 per-token input activations. Both are 8-bit weights, not identical.
  * `ngl`/`fa` are not vLLM concepts. Shown as 999/1 for column parity: all
    layers are on GPU, and flash attention is on via --attention-backend
    ROCM_AITER_FA.
  * pp2048 is measured as time-to-first-token for 2048 NEW tokens appended to a
    prefix-cached depth prefix. tg256 is (n-1)/(total - ttft) over a streamed
    256-token generation. llama-bench times these internally; these are
    client-side and include HTTP + scheduler overhead.
  * 3 reps per cell, mean ± stddev. Each rep uses a DIFFERENT 2048-token delta,
    salted per process run -- with --enable-prefix-caching on, reusing a delta
    replays it from cache and reports absurd rates (an earlier run of this same
    sweep produced 19,048 t/s at d8192 for exactly this reason).
  * d262144 is absent: served with --max-model-len 200000. The model's
    max_position_embeddings is 262144, so reaching it needs
    VLLM_ALLOW_LONG_MAX_MODEL_LEN=1 and a smaller KV budget.

REQUIRED PATCH -- without it these numbers are 3x lower

  vLLM gates ALL AITER usage behind is_aiter_found_and_supported() in
  vllm/_aiter_ops.py, which returns on_mi3xx() -- an MI300-series check that is
  False on gfx90a. AiterInt8ScaledMMLinearKernel (which calls gemm_a8w8_CK) was
  therefore never selected and W8A8 silently fell back to
  TritonInt8ScaledMMLinearKernel. build/enable_aiter_int8_gfx90a.py widens that
  gate to admit gfx90a while leaving on_mi3xx() itself untouched, so FP8/MXFP4
  paths stay correctly gated off (CDNA2 has no FP8 hardware).
