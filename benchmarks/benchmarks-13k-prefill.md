# 13K Token Cold/Hot Prefill Benchmarks

Standardized prefill benchmark comparing cold (no cache) vs hot (cache hit)
prefill performance across inference engines on identical AMD MI210 hardware.

Measured **2026-07-25**.

---

## Standardized Test

- **Prompt:** ~13,000 tokens — system instruction (~500 tok) + API documentation
  (~12K tok, 15 templated sections) + a short question
- **Deterministic:** same text every run (generated by `bench_prompt.py`)
- **Measured token count:** 13,048 tokens (DeepSeek-V2-Lite HF tokenizer)
- **Hardware:** 2× AMD MI210 (gfx90a, 64 GB HBM2e each), EPYC 74F3 (24c/48t),
  499 GB DDR4, PCIe 4.0 (no xGMI bridge), ROCm 7.14

### Measurement methodology

- **Cold prefill:** first request with the 13K prompt, no KV/prefix cache.
  Time = wall-clock from request start to response complete. Includes prefill
  + 50-token decode (same for both cold and hot, so the delta isolates prefill).
- **Hot prefill:** identical prompt sent immediately after cold. Prefix cache
  (vLLM APC) or in-context KV cache (llama.cpp `kv_unified`) should hit.
- **Decode speed:** short prompt (10 tokens), 200-token generation. Rate =
  output_tokens / wall-clock.
- All times are wall-clock (`time.time()` / HTTP round-trip).

## Results

| Setup | Cold Prefill (s) | Cold Rate (tok/s) | Hot Prefill (s) | Hot Rate (tok/s) | Cache Speedup | Decode (tok/s) |
|---|---:|---:|---:|---:|---:|---:|
| **vLLM TP=1** (DSV2-Lite BF16) | 3.49 | 3,743 | 2.27 | 5,753 | 1.54× | 23.9 |
| **vLLM TP=2** (DSV2-Lite BF16) | — | — | — | — | — | 21.7 ¹ |
| **llama.cpp** (DSV2-Lite q8_0, GPU) | 67.1 | 194 | 8.65 | 1,509 | 7.76× | 63.8 |
| **llama.cpp** (mimo 230B, CPU+GPU) | 197.6 | 63 | 5.19 | 2,389 | 38.1× | 20.8 |

¹ vLLM TP=2 decode from prior session (see Notes). Cold/hot prefill not measured
this session due to model-load timeout.

## Detailed Analysis

### vLLM TP=1 (DeepSeek-V2-Lite, BF16, single MI210)

| Metric | Value |
|---|---|
| Config | TP=1, BF16, `enforce_eager=True`, `gpu_memory_utilization=0.85` |
| Prefix caching | Enabled (APC) |
| Attention backend | Triton MLA (FLASH_ATTN MLA prefill) |
| MoE backend | TRITON Unquantized |
| KV cache | 776,128 tokens (22.48 GiB) |
| Model load time | 112.5 s |
| vLLM version | 0.25.2.dev0 |

**Cold:** 3.49 s for 13,048 tokens = **3,743 tok/s**. Includes first-time Triton
kernel JIT compilation overhead (~1 s for `fused_moe_kernel`,
`merge_attn_states_kernel`, flash-attn stage1/stage2).

**Hot:** 2.27 s = **5,753 tok/s**. The 1.22 s delta is the actual prefill
computation that the prefix cache eliminated. The remaining 2.27 s is 50-token
decode + scheduling overhead.

**Decode:** 23.9 tok/s. Consistent with prior measurements on this hardware.

### vLLM TP=2 (DeepSeek-V2-Lite, BF16, dual MI210)

| Metric | Value |
|---|---|
| Config | TP=2, BF16, `enforce_eager=True`, `gpu_memory_utilization=0.65` ² |
| Decode (prior session) | 21.7 tok/s |

² gpu_memory_utilization reduced from 0.85 to 0.65 because production llama.cpp
RPC servers occupy ~17 GB on each GPU, leaving ~47 GB free per card.

**Cold/hot prefill not measured:** Worker_TP0 safetensors loading stalled at 0%
for >12 minutes while Worker_TP1 completed in 34 s. This is the documented
~58-minute cold-load pathology for TP=2 on this system (see
[`changes/06-vllm-tp2-success.md`](../changes/06-vllm-tp2-success.md)). The
benchmark was abandoned at the 15-minute failure limit per task constraints.

### llama.cpp (DeepSeek-V2-Lite, q8_0, single MI210)

| Metric | Value |
|---|---|
| Model | `dsv2lite-q8_0.gguf` (16 GB) |
| Config | `-ngl 99 -c 16384 -fa on` |
| GPU | MI210 #0 (HIP_VISIBLE_DEVICES=0) |
| Flash Attention | Forced on (`-fa on`) — default `auto` crashes (SIGSEGV) |
| KV cache | Unified (`kv_unified=true`, 4 slots × 16,384 ctx) |
| Model load time | ~3 s |

**Cold:** 67.1 s for 13,055 tokens = **194 tok/s**. This is the raw prefill
speed with no cache. Slow compared to vLLM because llama.cpp processes the
prompt without batched/paged attention kernels optimized for MI210.

**Hot:** 8.65 s = **1,509 tok/s** with 13,054/13,055 tokens cached. The 7.76×
speedup shows the KV cache is highly effective — only the last few tokens need
reprocessing.

**Decode:** 63.8 tok/s — **2.7× faster than vLLM TP=1** (23.9 tok/s). This is
because q8_0 quantization halves memory bandwidth vs BF16, and decode is
memory-bandwidth-bound. The MoE expert selection also benefits from the
quantized weights being smaller to load.

### llama.cpp (mimo 230B MoE, CPU+GPU split via llama-swap)

| Metric | Value |
|---|---|
| Model | mimo (230B MoE, production) |
| Serving | llama-swap on port 8090 (25 CPU / 23 GPU layer split) |
| Quantization | q8_0 weights / q4_1 KV |
| Model load time | ~33 s (warm start from page cache) |

**Cold:** 197.6 s for 12,399 tokens = **63 tok/s**. This is a 230B model with
most layers on CPU — prefill is limited by CPU memory bandwidth and PCIe
transfer to GPU for the 23 GPU-resident layers.

**Hot:** 5.19 s = **2,389 tok/s** with 12,398/12,399 tokens cached. The 38×
speedup is dramatic — the KV cache eliminates virtually all CPU-side compute,
leaving only GPU-side attention for the cached tokens.

**Decode:** 20.8 tok/s. Limited by the CPU/GPU split architecture — each token
requires CPU-layer computation for the 25 CPU-resident layers.

## Cross-Engine Comparison

### Prefill speed (cold, no cache)

```
vLLM TP=1        ████████████████████████████████████████  3,743 tok/s
llama.cpp DSV2   ██                                         194 tok/s
llama.cpp mimo   █                                          63 tok/s
```

vLLM dominates cold prefill by **19×** over llama.cpp on the same model
(DeepSeek-V2-Lite) and **59×** over the 230B mimo. vLLM's Triton batched
attention kernels are far more efficient for long-context prefill than
llama.cpp's sequential processing.

### Hot prefill (cache hit)

```
llama.cpp mimo   ████████████████████████████████████████  2,389 tok/s
vLLM TP=1        ██████████████████████████████████████    5,753 tok/s ³
llama.cpp DSV2   ████████████████████████                  1,509 tok/s
```

³ vLLM's hot number is inflated because it includes 50-token decode time
(~2 s), making the prefill portion appear faster than the raw cache lookup.
The actual cache-hit delta (cold − hot = 1.22 s) shows the true prefill cost.

### Decode speed

```
llama.cpp DSV2   ████████████████████████████████████████  63.8 tok/s
vLLM TP=1        ████████████████                           23.9 tok/s
llama.cpp mimo   █████████████                              20.8 tok/s
vLLM TP=2        ██████████████                             21.7 tok/s
```

llama.cpp with q8_0 quantization is **2.7× faster at decode** than vLLM BF16
on the same model. Decode is memory-bandwidth-bound; q8_0 halves the bytes
per weight. TP=2 does not help decode (communication overhead negates the
bandwidth gain on PCIe-linked cards without xGMI).

---

## Key Findings

1. **vLLM wins prefill, llama.cpp wins decode.** vLLM's batched attention
   kernels process 13K tokens 19× faster cold. But llama.cpp's q8_0
   quantization gives 2.7× faster decode by halving memory bandwidth.

2. **Prefix/KV caching is universally effective.** All engines show
   significant hot-prefill speedup: 1.5× (vLLM), 7.8× (llama.cpp DSV2),
   38× (llama.cpp mimo). The mimo speedup is largest because its cold path
   is CPU-bottlenecked.

3. **TP=2 provides no decode benefit on PCIe-linked MI210.** Without xGMI,
   inter-GPU communication over PCIe adds latency that negates the bandwidth
   advantage of splitting across two GPUs. TP=2 decode (21.7) is actually
   slower than TP=1 (23.9).

4. **Flash Attention must be forced on for DSV2-Lite on gfx90a.** The
   default `-fa auto` detection crashes with SIGSEGV. Using `-fa on` works
   correctly and enables GPU-accelerated attention.

5. **vLLM TP=2 cold load is pathological.** Worker_TP0 stalls on safetensors
   loading (>12 min at 0% progress) while Worker_TP1 loads in 34 s. This
   reproduces the documented ~58-minute cold load. A warm (page-cached) load
   may be faster but was not tested.

## Reproduction

### Prompt generator

```python
# /tmp/bench_prompt.py — deterministic ~13K token prompt
from bench_prompt import get_prompt
prompt = get_prompt()  # 13,048 tokens (DSV2-Lite tokenizer)
```

### vLLM

```bash
docker exec vllm-single python3 /tmp/vllm_bench.py 1    # TP=1
# TP=2 requires ~58 min cold load:
docker exec <tp2-container> python3 /tmp/vllm_bench.py 2 0.65
```

### llama.cpp

```bash
docker run -d --name llama-dsv2-bench \
  --device /dev/kfd --device /dev/dri --group-add 991 \
  -v /mnt/llm-storage:/mnt/llm-storage:ro \
  -p 8095:8095 -e HIP_VISIBLE_DEVICES=0 \
  llama-rocm714:latest \
  -m /mnt/llm-storage/dsv2lite-q8_0.gguf \
  -c 16384 -ngl 99 -fa on --port 8095 --host 0.0.0.0

python3 /tmp/llama_bench.py
```

### mimo 230B (production llama-swap, do not restart)

```bash
python3 /tmp/llama_bench.py http://localhost 8090
```
